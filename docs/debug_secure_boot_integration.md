## 1. How the debugger works internally

The integrated debugger is [pulp-platform/riscv-dbg](https://github.com/pulp-platform/riscv-dbg),
an implementation of the RISC-V External Debug Support spec v0.13. It is
**execution-based**: the debug module never reads or writes core registers
directly. Instead it makes the core itself run small pieces of code, and the
core moves the data.

### 1.1 The chain from the JTAG pins to the core

```
 OpenOCD / TB BFM                                            SoC clock domain
 ──────────────                                   ────────────────────────────────────────────
 TCK TMS TDI TDO TRST                             ┌──────────────┐   debug_req   ┌──────────┐
   │                                              │   dm_top     │──────────────▶│   Ibex   │
   ▼                                              │ ┌──────────┐ │               │          │
┌───────────────┐  41-bit DMI  ┌──────────┐ DMI   │ │ dm_csrs  │ │  OBI slave    │ fetches  │
│ dmi_jtag_tap  │─────────────▶│ dmi_cdc  │──────▶│ │ (DM regs)│ │◀──────────────│ + loads/ │
│ (IR, DTMCS,   │   (TCK)      │ TCK→clk  │       │ ├──────────┤ │  0x1A11_xxxx  │ stores   │
│  DMI regs)    │              └──────────┘       │ │ dm_mem   │ │               │ in debug │
└───────────────┘                                 │ │ (debug   │ │               │   mode   │
     dmi_jtag.sv                                  │ │  memory) │ │               └──────────┘
                                                  │ ├──────────┤ │
                                                  │ │ dm_sba   │ │  (disabled: SbaEnable=0)
                                                  │ └──────────┘ │
                                                  └──────────────┘
```

| Layer | File | What it does |
|---|---|---|
| TAP | `rtl/riscv-dbg/src/dmi_jtag_tap.sv` | Standard JTAG state machine. 5-bit IR: `IDCODE=0x01`, `DTMCSR=0x10`, `DMIACCESS=0x11`. |
| DTM | `rtl/riscv-dbg/src/dmi_jtag.sv` | Turns a 41-bit DMI scan `{addr[6:0], data[31:0], op[1:0]}` into a DMI request. `op`: 1=read, 2=write. Response `op`: 0=ok, 2=error, 3=busy. `DTMCS` reports `version=1`, `abits=7`. |
| CDC | `rtl/riscv-dbg/src/dmi_cdc.sv` | Moves DMI requests/responses between the TCK domain and the SoC clock. |
| DM registers | `rtl/riscv-dbg/src/dm_csrs.sv` | The debugger-visible registers (below). |
| Debug memory | `rtl/riscv-dbg/src/dm_mem.sv` | A small memory the **core** reads and writes while halted: the debug ROM, the flags, the abstract-command program, the program buffer and `data0/1`. |
| OBI wrapper | `rtl/riscv-dbg/src/dm_obi_top.sv` | Turns dm_top's slave port into OBI: `gnt` always 1, `rvalid` one cycle later. |

**DM registers used** (DMI addresses):

| Addr | Register | Meaning |
|---|---|---|
| 0x04/0x05 | `data0`/`data1` | Values exchanged with the core |
| 0x10 | `dmcontrol` | `dmactive`, `haltreq`, `resumereq`, `ndmreset`, `ackhavereset`, `hartsel` |
| 0x11 | `dmstatus` | `allhalted`, `allrunning`, `allresumeack`, `allhavereset`, `version=2`, `authenticated` |
| 0x12 | `hartinfo` | `dataaccess=1`, `dataaddr=0x380`, `datasize=2`, `nscratch=2` |
| 0x16 | `abstractcs` | `busy`, `cmderr` (W1C), `progbufsize=8`, `datacount=2` |
| 0x17 | `command` | Abstract command (access register) |
| 0x18 | `abstractauto` | Re-run the last command when `data0` is accessed |
| 0x20-0x27 | `progbuf0-7` | Program buffer: 8 arbitrary instructions |
| 0x38 | `sbcs` | System Bus Access: **reported as unsupported** (`SbaEnable=0`) |

### 1.2 Debug memory map (`DmBaseAddress = 0x1A11_0000`)

The core reaches this region through `soc_addr_decode`: instruction fetches go
through `FSEL_DBG` and loads/stores through `SEL_DBG`, both arbitrated onto
the single DM OBI slave port.

| Offset | Name | Who writes / reads it |
|---|---|---|
| `0x100` | HALTED | Core writes its hart id when it enters the debug loop → DM sets `allhalted` |
| `0x108` | GOING | Core writes it when it starts a command → DM clears the GO flag |
| `0x110` | RESUMING | Core writes it when resuming → DM sets `allresumeack`, clears halted |
| `0x118` | EXCEPTION | Core writes it if a command faulted → DM sets `cmderr=3` |
| `0x300` | WHERETO | One `jal` generated by the DM: jumps to the abstract command or the progbuf |
| `0x338` | Abstract command | ≤10 instructions generated by the DM from `command` |
| `0x360` | Program buffer | `progbuf0-7` |
| `0x380` | `data0`, `data1` | The data registers as memory |
| `0x400` | FLAGS | One byte per hart: bit0 = GO (run a command), bit1 = RESUME |
| `0x800` | Debug ROM: halt entry | `DmHaltAddr` (Ibex jumps here on halt) |
| `0x808` | Debug ROM: resume | |
| `0x810` | Debug ROM: exception | `DmExceptionAddr` (Ibex jumps here on an exception in debug mode) |

### 1.3 What happens on a halt

1. The debugger writes `dmcontrol.haltreq=1`. `dm_csrs` raises `debug_req_o`,
   which drives Ibex `debug_req_i`.
2. The Ibex controller (`ibex_controller.sv`) finishes the instruction in
   ID/WB, then moves `DECODE → DBG_TAKEN_IF`. It:
   - saves the PC in `dpc` and the cause in `dcsr.cause` (3 = haltreq)
   - sets `debug_mode`
   - jumps to `DmHaltAddr = 0x1A11_0800`.
3. The core now **fetches the debug ROM** from the DM:
   ```
   0x800  j  _entry
   _entry: fence
           csrw dscratch0, s0          ; save s0
           csrw dscratch1, a0          ; save a0
           auipc a0, 0 ; srli a0,a0,12 ; slli a0,a0,12   ; a0 = DM base (0x1A110000)
   loop:   csrr s0, mhartid
           sw   s0, 0x100(a0)          ; HALTED  → dmstatus.allhalted = 1
           add  s0, s0, a0
           lbu  s0, 0x400(s0)          ; FLAGS[hartid]
           andi s0, s0, 1 ; bnez s0, going      ; GO?
           ...  andi 2 ; bnez resume            ; RESUME?
           j    loop
   ```
   Because the DM base is not 0, the ROM needs two scratch registers
   (`HasSndScratch`) and uses `a0` as the base pointer. That's why `s0` and
   `a0` are "special" registers during debug (see finding D08).
4. The core spins in `loop`. The debugger polls `dmstatus` until `allhalted=1`.

### 1.4 What happens on an abstract command (e.g. "read x9")

1. The debugger writes `command = {cmdtype=0, aarsize=2, transfer=1, write=0, regno=0x1009}`.
2. `dm_mem` generates this program at `0x338` and sets `FLAGS.GO`:
   ```
   csrw dscratch1, a0        ; a0 is borrowed as the base pointer
   auipc a0,0 ; srli/slli    ; a0 = DM base
   sw   x9, 0x380(a0)        ; x9 → data0   (a write command uses lw x9, 0x380(a0))
   csrr a0, dscratch1        ; restore a0
   ebreak                    ; back into the debug ROM
   ```
   For a **CSR** it uses `s0` as a temporary: `csrw dscratch0,s0 ; csrr s0,<csr> ; sw s0,0x380(a0) ; csrr s0,dscratch0`.
3. The ROM sees GO, writes GOING (`0x108`), jumps to WHERETO (`0x300`),
   which `jal`s to `0x338`. The command runs; `ebreak` in debug mode re-enters
   the ROM at `0x800`.
4. If an instruction faults (illegal CSR, bus error, DIFT violation…), Ibex
   jumps to `DmExceptionAddr` (`0x810`), the ROM writes EXCEPTION (`0x118`), and
   the DM sets `abstractcs.cmderr = 3`.
5. The debugger polls `abstractcs.busy`, then reads `data0` over DMI.

**postexec** (bit 18): the final `ebreak` becomes a `nop`, so execution falls
into the program buffer at `0x360`. That's how OpenOCD reads memory without
SBA: it writes an address into a register with an abstract command, then runs
`lw s1, 0(s0)` from progbuf.

### 1.5 Resume, single-step, reset

- **Resume**: `dmcontrol.resumereq=1` → the ROM sees RESUME, writes RESUMING
  (`0x110`), restores `s0`/`a0` from `dscratch0/1`, and runs `dret`: Ibex
  leaves debug mode and continues at `dpc`.
- **Single-step**: set `dcsr.step=1`, resume. Ibex executes one instruction
  and re-enters debug mode with `dcsr.cause = 4`.
- **ndmreset**: `dmcontrol.ndmreset=1` resets everything *except* the debug
  module (`sys_rst_n = rst_ni & ~ndmreset`), so the debugger keeps its
  connection while the core reboots.

### 1.6 Where the debugger touches SoC security

Everything the debugger does to the SoC is **done by the core in debug mode**.
That is the key to the whole integration:

- Ibex now exports `debug_mode_o`. `soc_addr_decode` uses it as `dbg_mode_i`, so
  the address decoder always knows when an access comes from the debugger.
- There is no SBA path, so there is no way around this.
- DIFT keeps running in debug mode, so the debug ROM and abstract commands are
  tag-tracked and policy-checked like normal code (Section 5).

## 2. Architecture changes and why

### A1. Debug module integrated as an execution-based slave (0x1A11_0000)
- **What**: `dm_obi_top` + `dmi_jtag` in `basic_soc_top`. The DM is reachable
  from both the fetch path and the data path, JTAG pins are top-level ports, and
  the DM runs on power-on reset while the rest of the SoC runs on
  `sys_rst_n = rst_ni & ~ndmreset`.
- **Why**: the debugger must be able to reset the core without resetting
  itself, and the core must fetch the debug ROM and access `data0` over normal
  buses.

### A2. No System Bus Access (`SbaEnable = 0`)
- **What**: new riscv-dbg parameter. `sbcs` reports no SBA and SBA triggers are ignored.
- **Why**:
  - SBA was advertised but its master port was tied off, so any SBA access hung
    forever (finding D14).
  - More importantly, SBA would be a second bus master that **bypasses the
    core**, and so bypasses every access rule below. Without it, all debugger
    memory traffic goes through the core and the decoder.

### A3. Hardware-enforced debug access policy
- **What**: in debug mode, the debugger
  - **cannot write** SoC CSRs (CTRL/BUF/SHA): the write gets an error
  - **cannot write** ISRAM (except in JTAG recovery)
  - **can read** CSRs and ISRAM
- **Why**: the rules existed on paper, but `dbg_mode_i` was tied to 0, and
  even when wired, `priv_write_ok` didn't look at it.

### A4. DIFT tag RAM covers DSRAM only; debugger stores are tagged untrusted
- **What**: the shadow tag RAM only accepts DSRAM addresses (others read tag 0
  and never write it), resets at power-on only, and tags every store made in
  debug mode as 1 (untrusted).
- **Why**: the tag RAM used to index *every* data address by `addr[11:2]`, so
  debug-module, ISRAM and peripheral accesses aliased onto DSRAM word tags.
  This caused findings D06b/D07/D11/D13: debug ROM stores wiped tags, and one
  unrelated tainted word could block the debugger. Tagging debugger writes as
  untrusted implements the rule that data coming from the debugger is not trusted.

### A5. JTAG recovery boot (`soc_recovery.sv`)
- **What**: a second way to boot when the bootrom is faulty.
  - **Entered by** a `boot_mode_i` strap sampled at power-on, or a **boot
    watchdog** (`boot_done` not set within N running cycles; paused in debug mode).
  - **In recovery**, `debug_req` is forced so the hart halts **before the first
    bootrom instruction** (re-armed by every `ndmreset`), and the debugger may
    write ISRAM until `boot_done`/`isram_lock`.
  - `STATUS0[2]/[3]` tell software that recovery happened and why.
- **Why**: a mask ROM can't be patched. Reusing the debugger (plus the
  verification gate) is the cheapest safe fallback using existing hardware.

### A6. Hardware-fed secure boot (`soc_secure_boot.sv`)
- **What**:
  - A feeder FSM reads the image **from ISRAM** and drives the unchanged
    `rtl/crypto/top_most` engine.
  - Software can only start a verification and read the result.
  - The public key comes from OTP.
  - A `verified` latch is cleared by any ISRAM write.
  - The fetch gate allows only `[entry, entry + 4·M)`.
  - The crypto clock is a clock-gated `clk/2` (synchronous, no CDC).
- **Why**: with CPU (or debugger) feeding, *what was hashed* and *what
  executes* can differ. In recovery, an attacker could feed a genuinely signed
  old image to the engine while malicious code sits in ISRAM. Hardware feeding
  binds the verdict to the exact bytes that run.

### A7. Full-SoC memory map and peripherals

| Region | Address | Notes |
|---|---|---|
| BootROM | `0x0000_0000` 4 KB | Data **reads** allowed before `boot_done` (A8) |
| ISRAM | `0x0001_0000` **8 KB** | Signed image lives here; enlarged from 4 KB |
| DSRAM | `0x0002_0000` 4 KB | DIFT-tagged |
| CTRL | `0x0003_0000` | `isram_lock`, `boot_done`, STATUS0 |
| VERIFY | `0x0005_0000` | `soc_secure_boot` registers |
| CLINT | `0x0200_0000` | `mtime`/`mtimecmp`/`msip` → `irq_timer`/`irq_software` |
| PLIC | `0x0C00_0000` | 12 sources → `irq_external` |
| QSPI (flash) | `0x1050_0000` | External boot flash |
| Timer | `0x1050_1000` | PULP `apb_timer` → PLIC source 5 |
| SPI #2 | `0x1050_2000` | General-purpose SPI master |
| UART | `0x1050_3000` | 16550-style → PLIC source 1 |
| GPIO | `0x1060_0000` | Waiting for the PULP `apb_gpio` IP (`HAS_GPIO`) |
| Debug | `0x1A11_0000` | riscv-dbg |

PLIC source IDs follow `software/soc.h`: UART=1, SPI=2, QSPI=3, GPIO=4,
TIMER=5, DIFT=8.

### A8. BootROM readable as data during the boot phase
- **Why**: boot code needs its own strings and constants, and a C bootrom puts
  `.rodata` in ROM. After `boot_done` the ROM is hidden from firmware again.

### A9. The boot flow
```
POR → BootROM @0x80: UART banner
    → QSPI: READ image header, then the whole image (8-word SPI bursts) → ISRAM (byte-exact)
    → CTRL0.isram_lock
    → VERIFY_CTRL.start → hardware feeder + SHA-512 + Ed25519 (~4 ms @ clk/2)
    → verified?  no → print error, halt (watchdog → JTAG recovery)
                 yes → read ENTRY, set boot_done, jump to 0x1_0044
    → firmware (vectored mtvec, UART/SPI/CLINT/PLIC ...)
```

## 3. RTL changes and why

### 3.1 Bug fixes

| # | File | Bug | Symptom | Fix |
|---|---|---|---|---|
| B1 | `soc_addr_decode.sv` DBG arbiter | The response was forwarded only while the request was still active | **The original halt hang**: after the debug ROM's `csrw` flush, Ibex dropped `instr_req`, two DM responses were thrown away, and the prefetcher waited forever | Latch the owner (`dbg_resp_is_data_q`) at accept, route `rvalid` by it |
| B2 | `soc_addr_decode.sv` ISRAM arbiter | `err` for a denied write was driven only in the request cycle | Denied ISRAM writes were silently dropped with `err=0` | Latch `isram_wr_denied_q`, return it with `rvalid` |
| B3 | `soc_addr_decode.sv` ISRAM arbiter | A fetch blocked by the verify gate got its `rvalid` overwritten with 0 | A blocked fetch **wedged** the core and fetch demux instead of faulting | Drive the blocked-fetch response after the routing block |
| B4 | `soc_addr_decode.sv` | `priv_write_ok` ignored `dbg_mode_i` | The debugger could write SoC CSRs during boot | `priv_write_ok = ~boot_done & (~dbg_mode \| (sha_hit & recovery))` |
| B5 | `ibex_wb_stage.sv` | With `WritebackStage=1`, load tags were never written to the tag register file | **DIFT couldn't propagate taint from memory at all** | Mux `rf_wdata_tag_lsu_i` / `rf_we_tag_lsu_i` into the WB tag outputs |
| B6 | `basic_soc_top.sv` tag RAM | `tag_addr` (already a word address) was indexed with `[TAG_AW+1:2]`: shifted twice | One tag per 4 words; neighbouring stores wiped a secret's taint | Index with `tag_addr[TAG_AW-1:0]` |
| B7 | `basic_soc_top.sv` APB mux | PULP slaves tie `PREADY=1`; `obi_to_apb` treats a ready in SETUP as the end of the transfer | **Every APB access hung** (first seen in full-SoC bring-up) | `pready &= penable` |
| B8 | `basic_soc_top.sv` UART | `apb_uart_sv` decodes `PADDR[2:0]`, but Ibex issues word addresses | Only THR/IER were reachable; writing LCR hit MCR | Feed `paddr[11:2]`: register n at +4·n (matches `soc.h`) |
| B9 | `basic_soc_top.sv` SPI #2 | Standard-mode RX samples `sdi1`, not `sdi0` | SPI #2 could never receive (same bug in `sentinel_soc_top`) | MISO → `sdi1` |
| B10 | `basic_soc_top.sv` tag RAM, `dsram_model.sv` | `always_ff` forbids a second writer | Testbench taint injection wouldn't elaborate (`MULAXX`) | Plain `always` (synthesizes identically) |

## 4. Test methodology

### 4.1 Common principles
- **Black-box stimulus through real pins**: JTAG pins for debug tests; only
  power-on reset for the full SoC. No `force`/`deposit` into the core or the DM.
- **Self-checking with result classes**:
  - `[PASS]`/`[FAIL]`: functional behaviour.
  - `[FINDING]`: debug works but a DIFT/security property breaks (a design
    review item, not a regression).
  - `[OBS]`: recorded behaviour.
- **Backdoors only where the testbench plays a role the real system gives
  another agent**: preloading memories, forcing the OTP key ("fusing"), and
  injecting taint into the tag RAM.
- **Monitors report internal events** (debug-mode exceptions, DIFT events,
  NMIs) to explain failures, never to stimulate.

### 4.2 Debugger testbenches (`verif/debugger/`)

| Testbench | Filelist | Scope |
|---|---|---|
| `dbg_tb_top.sv` | `files.f` | Smoke test: activate DM, halt, write/read x1, resume |
| `dift_dbg_tb.sv` | `files_dift_dbg.f` | Debug spec + DIFT + JTAG recovery, with the verdict faked through the legacy `crypto_verified` pin (`SECURE_BOOT=0`) |
| `secure_boot_dbg_tb.sv` | `files_secure_boot_dbg.f` | Everything above + hardware secure boot (142 checks) |

**The JTAG BFM** (`interface/jtag_if.sv`) bit-bangs TCK/TMS/TDI:
`tap_reset`, `shift_ir`, `shift_dr`, and `dmi_read`/`dmi_write`. Each op is
followed by a NOP scan to fetch the result, retrying on `BUSY`, exactly like
OpenOCD. One DMI op takes about 7 µs of simulated time.

**Firmware inside the testbench**: the testbench assembles a small program and
backdoor-loads it into the BootROM model. It reads its configuration
(TPR/TCR, secret values, whether to set `boot_done`) from DSRAM, loads
"secrets" into `s0/a0/t1/s1`, arms TCR last, then loops writing a heartbeat to
DSRAM.

**Scenario = one SoC boot**: `boot()` holds the core in `ndmreset`, writes
config and taint (`u_dut.tag_mem[...]`), releases, waits for the heartbeat,
and checks that GPR tags match the injected taint.

**Parts**:
- **A (debug spec)**:
  - DTM: IDCODE, DTMCS.
  - DM: `dmstatus`/`hartinfo`/`abstractcs`.
  - Halt: cause and `dpc`, re-halt.
  - Register/CSR access: GPR patterns, x0, s0/a0 (dscratch-backed), CSRs.
  - Errors: unimplemented CSR (`cmderr=3`), 64-bit access (`cmderr=2`), quick access.
  - Program buffer: incl. illegal instruction and transfer + postexec; autoexec.
  - Stepping and resume: single-step (`dpc` advances by one, cause 4), resume.
  - Other: command while running (`cmderr=4`), `hartsel` WARL, `dmactive` toggle.
- **B (DIFT × debug)**:
  - S1: tag bookkeeping.
  - S2: full policy, TCR/TPR lockout, tainted reads, violations inside progbuf.
  - S5: `dift_en=0`.
  - S3: tainted `s0`.
  - S4/S6: tag aliasing and X tags.
- **D (access policy)**:
  - D-TAG: debugger stores into DSRAM are untrusted.
  - D-PRIV: no CSR/ISRAM writes, reads OK, no verify start outside recovery,
    watchdog paused while halted.
- **C (no SBA)**: `sbcs` advertises nothing; forced SBA pokes are ignored.
- **E (recovery + secure boot)**, with power-on resets and a faulty bootrom:
  - **R-STRAP**:
    1. halted at `0x80`, 0 instructions executed
    2. image loaded through the debugger
    3. unverified image faults
    4. tampered image rejected
    5. one-shot error
    6. `ndmreset` re-halts
    7. signed image verified
    8. header not executable
    9. runs
  - **R-WDT**: the watchdog forces recovery; an ISRAM write after verification clears `verified`; re-verify runs.
  - **R-NORMAL**: good ROM, no recovery.

**Unit test**: `verif/secure_boot/tb_secure_boot.sv` (Verilator,
`run_verilator.sh`). It runs `soc_secure_boot` with the real crypto RTL on a
signed image and a tampered one, checking the hash, verdict and fetch gate.
It takes seconds.

### 4.3 SoC + crypto (secure boot)
- **Image format** (`software/tools/sign_image.py`, `rtl/crypto/scripts/build_mem.py`):
  `[be32 sha_len = 16 + M][R 32B][S 32B][code M words]`. Ed25519 over the code
  bytes; the public key is in OTP, never in the image.
- **Keys**: a fixed **test-only** seed (reproducible images). The debug
  testbenches and the full SoC use the same key (`otp_pubkey.mem`).
- **Coverage**:
  - good, tampered and swapped-after-verify images
  - the header and the tail past the code are not executable
  - one-shot per reset
  - a debugger-started verify is allowed only in recovery
  - unverified code faults (without wedging) and the debugger can still halt

### 4.4 Full SoC (`verif/soc/full_soc_tb.sv`)
- **Stimulus**: power-on reset only.
- **Models**:
  - BootROM (`verif/soc/images/bootrom.hex`)
  - ISRAM/DSRAM
  - `spi_flash_model.sv`: mode 0, READ `0x03`, JEDEC `0x9F`, preloaded with the signed image
  - OTP key force
- **Observers**:
  - a UART decoder on the `uart_tx` pin (8N1, 16 cycles per bit), producing a transcript
  - an SPI #2 pin monitor
  - DSRAM result words written by the firmware
- **Checks**:
  - ROM banner
  - image read over SPI (count of READ commands)
  - VERIFIED, then `boot_done`
  - firmware prints from ISRAM
  - SPI #2 byte `0xA5`
  - CLINT interrupt count = 1
  - PLIC claimed source 5
  - result `0xB007B007`
  - no errors
- **`+TAMPER`**: flips one firmware bit in flash. The ROM must report the
  failure; no `boot_done`, no firmware.
- **`+TRACE`**: bounded bring-up trace (fetches, data bus, APB, traps, FSM).
  This is how B7 and the two firmware bugs were found.
- **Software**:
  - `software/boot/bootrom.S` and `software/app/app_demo.S` (GNU assembly)
  - built by `software/tools/rvasm.py`, a small assembler cross-checked
    byte-exact against riscv-dbg's debug ROM and an image that ran on Ibex
  - signed by `sign_image.py`
  - `software/build_sim_images.sh` does all three.

## 5. The five "DIFT-FINDINGS" in every run

`dift_dbg_tb` and `secure_boot_dbg_tb` end with
`DIFT-FINDINGS=5`. These are **not failures**: debug works correctly. Each one
is a place where **DIFT semantics break when the debugger is involved**. The
testbench reports them so they stay visible until a design decision closes
them.

Background: DIFT gives every GPR and every DSRAM word a 1-bit tag
(1 = untrusted/tainted). `TPR` decides how tags propagate (AND/OR/clear per
instruction class). `TCR` decides which uses of tainted data fault (jump
target, branch operand, load/store address or data, ALU operands...).
Violations either raise a synchronous exception (`ex_tag_err`) or pulse the
DIFT interrupt (`irq_nm`).

### D06a: a debugger register write clears the register's taint
- **Seen in**: S1. `t1` is tainted; the debugger writes `t1` → tag becomes 0.
- **Why**: an abstract register write executes `lw t1, 0x380(a0)`, loading
  from the DM's `data0`. The DM is not DSRAM, so the tag RAM returns tag 0, and
  the loaded value is "clean".
- **Risk**: a debugger can *launder* a value into firmware as trusted data.
- **Options**:
  - (a) Accept it: the debugger is trusted during development.
  - (b) Return tag 1 for loads from the DM data window in debug mode
    (`0x1A11_0380..0x387`), so debugger-supplied registers become untrusted,
    like debugger stores to DSRAM. With TCR bit 6 set, this makes debugger
    register writes fault: the debugger becomes read-only by policy.

### D08a / D08b: `s0` and `a0` lose their taint across halt/resume
- **Seen in**: S1. Tainted `s0`/`a0` come back clean after halt → resume.
- **Why**: the debug ROM uses `s0` and `a0` as scratch registers (Section 1.3).
  It saves their **values** in `dscratch0/1` and restores them with `csrr`, but
  CSRs have no tag bit. Meanwhile the ROM recomputes `a0` with
  `auipc/srli/slli` and overwrites `s0` with `lbu` from FLAGS, both of which
  write clean tags. On resume the values come back but the tags don't.
- **Risk**: any halt/resume, even a harmless breakpoint, launders the taint of
  two registers.
- **Options**:
  - (a) Freeze tag register file writes while `debug_mode` is set (tags survive
    untouched; but abstract writes would then keep the *old* tag).
  - (b) Add tag bits to `dscratch0/1` and save/restore them with the value.

### D03: a tainted register can be read out over JTAG
- **Seen in**: S2. `t1` holds a tainted secret; an abstract read returns it in `data0`.
- **Why**:
  - An abstract read is `sw t1, 0x380(a0)`, a store to the DM, not DSRAM, so
    no tag-RAM check applies.
  - The core's DIFT store check (`lsu_tag_err`) only fires on the store
    **response**, after the write has already happened. Before DSRAM-only
    tagging it did fire (`cmderr=3`), but the secret was already in `data0`.
- **Risk**: the debugger is an unchecked exfiltration path for tainted secrets.
- **Options**:
  - (a) Accept it while JTAG is enabled only in development/recovery.
  - (b) Block stores of tainted data to the DM window in debug mode (check the
    store-data tag at the request, not the response).
  - (c) Debug authentication / lifecycle lock (riscv-dbg hardwires `authenticated=1`).

### D12: `dift_en_i = 0` does not fully disable DIFT
- **Seen in**: S5. With `dift_en_i=0`, a tainted source still faults
  program-buffer code (`addi s1, t1, 0` → `cmderr=3`).
- **Why**: `dift_en_i` only masks memory tags and the DIFT interrupt
  (`ibex_core.sv:427, 565`). The synchronous violation path into the
  controller (`ex_tag_err_i = ex_exception | pc_exception`, `ibex_core.sv:884`)
  is not gated, and the GPR tags already set keep faulting.
- **Risk**: "DIFT off" isn't off; old tags can still cause faults (affects normal code too).
- **Fix** (small, low risk): gate `ex_exception | pc_exception` with `dift_en_i`.

### Findings that were *closed* on these branches
- **D07a/b, D06b, D11, D13**: fixed by DSRAM-only tagging (A4 / B6).
- **D14**: fixed by `SbaEnable=0` (A2).
- **D10** (a tainted `s0` breaking halting): predicted, not reproduced. The ROM's
  `csrr s0, mhartid` clears `s0`'s tag before any check sees it (same root
  cause as D08a).

## 6. How to run everything

From the repo root on the Xcelium server:

```bash
# debugger
xrun -f verif/debugger/files.f                 -l dbg.log              # smoke
xrun -f verif/debugger/files_dift_dbg.f        -l dift_dbg.log         # debug + DIFT + recovery (legacy verify)
xrun -f verif/debugger/files_secure_boot_dbg.f -l secure_boot_dbg.log  # + hardware secure boot

# secure boot unit test (Verilator, seconds)
verif/secure_boot/run_verilator.sh

# full SoC
./software/build_sim_images.sh                                         # rebuild ROM + signed image
xrun -f verif/soc/files_full_soc.f -l full_soc.log                     # normal boot
xrun -f verif/soc/files_full_soc.f -l full_soc_tamper.log +TAMPER      # tampered firmware
xrun -f verif/soc/files_full_soc.f -l full_soc.log +TRACE              # bring-up trace

grep -E "\[(PASS|FAIL|FINDING|OBS)\]|checks=|TEST|UART \|" <log>
```

map), DIFT exercised by real firmware, and decisions on D03/D06a/D08/D12.
